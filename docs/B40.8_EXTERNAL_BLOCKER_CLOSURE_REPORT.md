## 7. Gate D — payment and financial regressions

**Status: NOT VERIFIED — no database-backed payment or security tests ran.**

### Source and test review

Static inspection covered `apps/api/src/controllers/ordersController.ts`,
`apps/api/src/services/paymentService.ts`, and existing tests including
`paymentConcurrency.test.ts`, `paymentIdempotency.test.ts`,
`paymentAmountIntegrity.test.ts`, `orderPaymentIntegrity.test.ts`,
`paymentStateMachine.test.ts`, `refundSecurity.test.ts`,
`folioFinancialIntegrity.test.ts`, `bankPayment.test.ts`,
`mpesaSecurity.test.ts`, `stripeSecurity.test.ts`, and
`paymentTenantIsolation.test.ts`.

The reviewed code/test structure provides the following source-level evidence:

1. **Same key/same request:** order payment performs an initial lookup and
   rechecks under a transaction-scoped advisory lock; matching retries return
   the existing row. Tests assert a single persisted payment and deduplicated
   replay.
2. **Concurrent collection limit:** order collection re-locks and revalidates
   the order in a transaction and applies a balance-guarded ledger update.
   The payment insert and ledger update are in that transaction; failure of
   the guarded update throws, rolling back the insert. Concurrency tests
   inspect persisted rows, aggregate amounts, paid amount, and balance rather
   than inferring overpayment from successful HTTP responses alone.
3. **Legitimate partial payments:** a concurrency regression requires two
   distinct half-total payments to succeed and checks aggregate and ledger
   totals.
4. **Cancelled orders:** the order-pay endpoint rejects non-collectable
   states and rechecks after acquiring the row lock. Existing tests include a
   cancelled-order case and a cancellation/row-lock race.
5. **Rollback:** the concurrency test checks that only one full-balance
   payment row persists after simultaneous attempts; transaction boundaries
   were inspected. These assertions were not executed in B40.8.
6. **Provider/method and callback state:** implementation validates payment
   method/provider values and reconciles provider, currency, and amount against
   the stored payment. Existing Stripe/M-Pesa cases cover wrong provider or
   anchor, amount/currency mismatches, replay, and terminal-state callbacks.
7. **Refund and folio invariants:** tests inspect refunded totals/status,
   folio balances and transaction counts, tenant ownership, and concurrent
   operations.
8. **Bank verification/state transitions:** bank tests cover submission,
   verification/rejection, permissions, cancelled orders, and idempotency.
9. **Tenant isolation/authorization:** payment and folio tests cover
   cross-tenant reads, writes, refunds, settlement, and unauthorized callers.

These observations are not test results. No runtime financial defect was
confirmed by this source review. No code, business rule, or test assertion was
changed. The prior B40.4/B40.5/B40.7 concurrency observations remain historical
reports and were not independently reproduced.
