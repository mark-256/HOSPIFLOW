## 4. Test-database recovery and safe setup

**Current database identity: NOT VERIFIED. No database connection was attempted.**

`DATABASE_TEST_URL` was absent from the current process. The root and
`apps/api/.env` files exist and contain a `DATABASE_URL` key, but neither
contains a `DATABASE_TEST_URL` key. Their values were not displayed or copied.
The API Vitest configuration reads `process.env.DATABASE_TEST_URL` directly and
does not load dotenv; its guard refuses to run rather than falling back to
`DATABASE_URL`. This is why the current test process has no test URL. With no
explicit URL, neither a local host nor the dedicated `hospiflow_test` database
could be verified.

Safety corrections made:

- The integration-test environment now refuses any database name other than
  `hospiflow_test` and any host other than localhost/loopback.
- PostgreSQL URL parsing now accepts both `postgres://` and
  `postgresql://` forms when checking the configured database identity.
- The setup script now enforces the same local, dedicated database identity
  before database creation or migration.
- Test setup diagnostics no longer print database URLs or credentials.
- The setup script was not run, and no database was created or migrated.

When a local PostgreSQL instance is available, configure the URL without
echoing it or adding it to this report:

```sh
read -r -s -p 'Local DATABASE_TEST_URL: ' DATABASE_TEST_URL
printf '\n'
export DATABASE_TEST_URL
scripts/setup-test-db.sh
```

The entered URL must resolve to a local host (`localhost`, `127.0.0.1`, or
`::1`) and the database `hospiflow_test`. The script refuses other hosts or
database names, then creates the dedicated local database if needed and applies
the database migrations only to that test target. If local PostgreSQL or the
database-creation role is unavailable, the local developer/database
administrator must provision the dedicated database and grant the necessary
local permissions; do not substitute a remote or production endpoint.

After successful local setup and identity verification, run the following from

## 5. B40.5 payment-integrity review

Static review of the current order-payment controller and
`paymentConcurrency.test.ts` confirms the following protections and assertions
remain present:

- Same-key requests take a transaction-scoped advisory lock, recheck for an
  existing payment, and return the existing record rather than creating a
  duplicate collection. Tests assert one record for concurrent same-key
  initiation and one collection for same-key retries racing order-item changes.
- The payment transaction locks the order row with `FOR UPDATE`, rechecks
  collectable state while holding the lock, and records the payment and order
  collection transactionally.
- The partial-payment test asserts that two distinct concurrent partial
  payments can succeed while their aggregate remains within the order total.
- Cancellation/payment race coverage includes a test that waits for the order
  row lock and asserts the payment is rejected after cancellation.
- The unkeyed concurrent-payment test and its balance/collection assertions
  remain present.

These are source and test-inventory observations, not new runtime verification.
Because the database-backed suite was not run, this report does **not** claim
that the original unkeyed concurrency scenario has been reproduced or fixed.
The code was not refactored outside the test-environment safety changes.
