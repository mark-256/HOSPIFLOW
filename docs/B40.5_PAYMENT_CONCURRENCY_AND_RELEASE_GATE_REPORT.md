## 2. Payment concurrency investigation and correction

### Endpoint and observed three-success assertion

The failing test calls `POST /api/orders/:id/pay`, registered in
[`orders.ts`](../apps/api/src/routes/orders.ts) and implemented by
[`ordersController.pay`](../apps/api/src/controllers/ordersController.ts).
It does not call `paymentService.initiatePayment`.

The test that previously expected at most one `201` sent five simultaneous
requests **without an `Idempotency-Key`**, each for the order's then-current
full total, while five requests added more items. Without an idempotency key,
the server cannot distinguish a retry from a second intentional collection.
The existing endpoint supports distinct partial payments; once concurrent item
additions increase the total and balance, repeated amounts can be legitimate
partial payments. The earlier B40.4 evidence records two full-suite runs with
three `201` responses, while
the aggregate paid amount, order `paidAmount`, and balance remained within the
final order total. The test's `pays.length <= 1` assertion therefore did not
establish duplicate financial records or an overpayment. If unkeyed identical
requests are meant to be retries rather than distinct collections, that
business rule remains unspecified; this correction uses the established
`Idempotency-Key` contract to make retry identity explicit.

This task's first attempt to run that pre-change test was blocked during Prisma
setup as described above, so the exact historical three-`201` result was not
independently reproduced in this session. The original failure is supported by
the repeated B40.4 run evidence and by the request shape and transaction
semantics below.

### Transaction, isolation, idempotency, and provider behavior

- The endpoint initially reads order status and balance outside its write
  transaction. It then creates a completed `OrderPayment` and calls
  `recordOrderCollection` in the same Prisma transaction.
- `recordOrderCollection` performs one conditional SQL update guarded by the
  *current* `balance >= amount`. PostgreSQL row updates serialize, and a failed
  ledger update throws, rolling the newly created payment back with the
  transaction.
- The local test database reports PostgreSQL's default isolation as
  `read committed`. The endpoint did not specify a transaction isolation
  override.
- `OrderPayment` had no idempotency-key column or unique constraint. Its only
  non-primary-key index was on `orderId`. The optional endpoint key was checked
  before the transaction by looking up `reference`; two concurrent partial
  requests with the same key could both miss that lookup and create financial
  rows. A caller-provided `reference` could also take precedence over the key.
- The payment endpoint makes no provider call: it records this direct/manual
  collection as completed. The separate provider initiation service creates a
  durable `PENDING` row under its idempotency lock before calling the adapter;
  provider initiation therefore occurs after reservation.

### Change and regression evidence

The endpoint now:

1. Takes a transaction-scoped advisory lock for the order and idempotency key.
2. Re-reads the key inside the transaction, matching either legacy
   `reference` values or the new key metadata. Identical replays return the
   original row with HTTP 200; amount or method changes remain rejected.
3. Locks and revalidates the current order state before inserting a new
   payment. The atomic guarded balance update and payment insert remain in the
   same transaction, so losing a balance race rolls the insert back.
4. Stores the key in payment metadata without taking precedence over the
   caller's separate provider/reference field.

Different idempotency keys, and unkeyed requests, remain distinct payment
attempts. Legitimate partial payments are not deduplicated or disallowed.

The formerly failing item-addition scenario now identifies its five repeated
requests with one key, requires exactly one `201`, four idempotent `200`
responses, and one persisted payment. The existing simultaneous full-payment
test additionally requires one persisted row and nine controlled `400`
responses, exercising rollback. The partial-payment test requires exactly two
successful half-total collections; it continues to assert the total and
remaining balance constraints.
